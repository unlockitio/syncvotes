# syncvotes-concordia

Independent Daml package (`daml/concordia/daml.yaml`, source `src/SyncVotes/Concordia/`). It does not depend on the original `syncvotes` DAR. Dependency DARs are generated in `lib/` by `python3 scripts/build-concordia-deps.py`; no sibling Concordia checkout is needed. Build with `~/.dpm/bin/dpm build --all` from the SyncVotes root and test with `~/.dpm/bin/dpm test --package-root daml/tests/concordia`. The tests remain separate from the original SyncVotes suite. `Proposal_Tally` is controlled by the provider, who observes the `Round` and each `Ballot` so the provider can fetch presented ballots; the creator remains its signatory and execution authorizer. Removing the former operator field changes the `Round` schema, while tally authority now belongs to the provider rather than the former operator. Existing rounds and consumers need an explicit migration; ledger contracts are not rewritten.

Renaming the concrete `Proposal` template to `ProposalAction` changes its Daml template identity even though its five fields and behavior are unchanged. Existing `Proposal` contracts are not automatically migrated to `ProposalAction`: ledger consumers must update template references and arrange an explicit archive/recreate or other governed migration before relying on existing contracts. Package version remains 0.1.0; the only known dependent DAR is the in-repo test package. Renaming `owner` to `creator` on `ProposalAction`, `ProposalExecution`, `Round`, `Ballot` and `Target` changes their Daml record schemas despite retaining the same party, signatories and authority. Existing contracts and consumers of those fields need an explicit migration and updated bindings; the rename does not rewrite ledger data.

`Types` keeps the shared data shapes alone (Vote, Outcome, Effect, Basis, Threshold, Rule, Settings) and imports nothing, so it cannot take part in a cycle. `Rules` owns rule, settings, option, share-change, label and image validation plus `changesDao`, `batch` and `maxChanges`; `Tally` owns `Counts`, `add`, `meets` and `decide`. Both import `Types` one way, matching the original `SyncVotes.Rules` and `SyncVotes.Tally` ownership. Consumers import the owning module explicitly; the split moves no arithmetic, eligibility or early-resolution semantics and changes no data type, choice or authority. `Round` retains a separate voting snapshot and ballot roll: folding it into `ProposalAction` would change the proposal's signatories and observers, its initial creation, and the independent lifecycle of the Action contract. `Member_Cast` remains a party-controlled choice on `Round`, unlike the original choice on `Member` controlled by `party`. The fork records the voter in `Round.roll`, checked-fetches a live `Member` against the opening electorate and share, and consumes and recreates `Round` when casting or replacing a ballot. Moving the choice onto `Member` without moving those checks would falsely suggest a member-only gate; moving the templates or adding an interface here would change template identity or package upgradeability. This is an explicit placement gap, not full ledger parity. `Proposal_Tally` remains provider-controlled on `Round`. `Member` owns the member template and checked weight instance; `Target` owns the Concordia target template and binding helpers, which have no honest original module counterpart. `Keys` holds shared Concordia resolver and authentic-key construction; neither it nor `Target` corresponds to the original billing, markers, or account modules. `Governance` keeps `ProposalAction`, `ProposalExecution` and `DAO` together because `DAO_Open` fetches the concrete `ProposalAction` while `ProposalExecution` exercises `DAO_Apply`; splitting those dependencies would create an import cycle. `Account` owns the account template in its own original-named module: it only needs `DAO`, `Member` and `Types`, so importing `Governance` one way introduces no cycle. Moving `Account` out of `Governance` changes its Daml template identity even though its fields, signatories, observer, choice body and authority are unchanged; existing `Account` contracts are not automatically migrated and consumers must update template references. `ProposalExecution` is the sole standing-contract naming gap: the original `DAO_Execute` executes inline, while Concordia requires a distinct authorized Executable contract.

The test vocabulary aliases below are literal delegations to `Fixtures`, not separate ledger implementations. Primitives in the last column run **inside the ledger choice**, never in the alias or helper. `ProposalAction` is the concrete action template (not `Proposal`), and its authority field is `creator` (not `owner`). The original `Member.party` controls a choice on `Member`; in this fork `Round.Member_Cast` is controlled by `voter` and remains the placement exception described above. `Round.Proposal_Tally` is controlled by `provider`.

**Deliberately local arithmetic:** `Cap.Governance.Utils.Count.rule`, `shareOfTotal` and `shareOfVotes` are not called. `rule` composes a quorum and single tally verdict, but does not supply this package's early/outstanding-vote logic. `shareOfTotal` counts only `Some` votes as turnout, whereas quorum here includes abstentions. `shareOfVotes` selects exactly one qualifying option over voted weight; it cannot represent `OfAll`'s whole-electorate basis or the multi-pick denominator (weight of voters who picked, counted once per voter). `Tally.decide` uses the opening electorate and these distinct denominators instead.

Founders are observers of `FoundingProposal` so they can see the terms they accept; this discloses the proposed share allocation to all founders on the enforced standard pre-DAO consent path, not a vote, while the privileged `Account_CreateDAO` path remains intentionally reachable without consent.
The invitee observes `MembershipInvitation` and sees the proposed share before accepting the standard direct-approval admission path, not a vote; direct privileged `DAO_ChangeShares` remains intentionally reachable without consent.

`Signal`, `Choose`, `SetInfo`, `SetRules`, `SetPublic`, `SetSettings` and `Dissolve` can flow through Action authorization and Executable execution. `SetShares` has no executable: shares change administratively via `DAO_ChangeShares`. `DAO_Apply` is separately callable with **joint provider and creator authority**; interface execution is not a vote-only enforcement boundary for that choice. It is not renamed `DAO_Execute`: the original choice executes a passed proposal, while this choice accepts an effect directly. `DAO_Open` remains on DAO because the creator opens a separately created Action with an electorate snapshot; the original `Member_Propose` is controlled by the member and creates the proposal itself. `Account_CreateDAO` retains the original name for account-led founding, without implying a vote-gated founding path. `Ballot_Consume` remains distinct from original `Ballot_Count` (which records a counted ballot) and `Ballot_Withdraw` (voter-controlled): here the creator consumes ballots. `BallotV2` and `Comment` are absent rather than relabeled; no equivalent responsibilities exist in this package.
