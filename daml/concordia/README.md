# syncvotes-concordia

Independent Daml package (`daml/concordia/daml.yaml`, source `src/SyncVotes/Concordia/`). It does not depend on the original `syncvotes` DAR. Dependency DARs are generated in `lib/` by `python3 scripts/build-concordia-deps.py`; no sibling Concordia checkout is needed. Build with `~/.dpm/bin/dpm build --all` from the SyncVotes root and test with `~/.dpm/bin/dpm test --package-root daml/tests/concordia`. The tests remain separate from the original SyncVotes suite.

| Concordia primitive | Consumer in `SyncVotes.Concordia.*` |
| --- | --- |
| `Cap.Governance.ActionV1.Action` | `Governance.Proposal` implements `view` (authorizers and binds), `action_readStateImpl` (reads `DAO` or `Target` state) and `action_authorizeExecutionImpl` (checks authority/outcome, merges binds, creates `ProposalExecution`). `Proposal_Tally` exercises `Action_AuthorizeExecution`. |
| `Cap.Governance.ExecutableV1.Executable` | `Governance.ProposalExecution` implements `view`, `executable_executeImpl` (checks targets, executes `Signal`, `Choose` or a DAO change) and `executable_cancelImpl`. The interface choices enforce execution entitlement/window, cancellation entitlement/window and expiry. |
| `Cap.Governance.Utils.Weights.HasWeight` | `Member.Member`: `weightOf` returns member party and decimal share; `DAO_Open` reads these weights for the electorate snapshot. |
| `Cap.Governance.Utils.Ballots.IsBallot` | `Round.Ballot`: exposes voter/cast, pins and action CID; `consume` exercises `Ballot_Consume`. |
| `Cap.Governance.Utils.Targets.HasState` | `Governance.DAO` exposes its encoded mutable state; `Target.Target` exposes `info`. Both are read by the action's target reader and checked against pinned state. |
| `Splice.Util.HasCheckedFetch` | `Member.Member` under `Keys.memberKey(provider, creator, daoId, party)`; `Governance.DAO` under `Keys.daoKey(provider, creator, daoId)`; `Target.Target` under `signedKey label target` (corresponding to `Keys.targetKey(owner, label)`); `Round.Ballot` under its `Mechanism`. |
| `Cap.Core.Types.AuthenticKey` | `Keys` constructs DAO, member and target identities from authorities and identifiers; `Governance` and `Round` use them for weights, binds and checked target/member fetches. |
| `Cap.Core.Types.ExecutionCore` / `ExecutionAction` | `Proposal_Tally` issues a core with owner authority, `EA_Execute` for `[owner]`, opening time and expiry; `Governance.ProposalExecution` stores it. No `EA_Cancel` entitlement is issued. |
| `readWeights` | `Governance.DAO_Open` reads checked member sources, then snapshots weights and shares. |
| `weighBallots` / `consumeBallots` | `Proposal_Tally` checks ballot casts against opening weights and consumes presented ballots after deciding. Local `Types.add`/`decide` performs the actual arithmetic. |
| `fetchGroup` / `requireMechanism` | `Proposal_Tally` checks the resolver/procedure and checked-fetches the nonempty, distinct ballot group against its mechanism. |
| `pinStatesWith` | `Member_Cast` reads the action's open target binds and pins presented target state into each ballot. |
| `checkTarget` | `Target.setInfo` checks a pinned `Target` before `Target_SetInfo`; `Governance.ProposalExecution` checks a pinned `DAO` before `DAO_Apply`. Both use equality for state drift. |
| `requireSameKeys` | `ProposalExecution.executable_executeImpl` requires exact bound target keys at execution. |
| `mergeBinds` | `Proposal.action_authorizeExecutionImpl` merges action binds with the round's ballot pins. |
| `admitActors` / `entitled` / `requireOpen` | Called by Concordia's `Action_AuthorizeExecution` and `Executable_Execute`/`Executable_Cancel` interface choices, not directly by this package. They check action authorizers, available execution/cancellation actors and time windows respectively. |

`Types` keeps Vote, Outcome, Effect, Rule, Settings, validation and tally together: splitting the small pure seam into Types/Rules/Tally would add imports without separating ledger responsibilities. `Round` retains a separate voting snapshot and ballot roll: folding it into `Proposal` would change the proposal's signatories and observers, its initial creation, and the independent lifecycle of the Action contract. `Member_Cast` and `Proposal_Tally` name the corresponding operations, though Daml defines them on `Round` to preserve their controllers and behavior. `Member` owns the member template and checked weight instance; `Target` owns the Concordia target template and binding helpers, which have no honest original module counterpart. `Keys` holds shared Concordia resolver and authentic-key construction; neither it nor `Target` corresponds to the original billing, markers, or account modules. `Governance` keeps `Proposal`, `ProposalExecution`, `Account` and `DAO` together because `DAO_Open` fetches the concrete `Proposal` while `ProposalExecution` exercises `DAO_Apply`; splitting those dependencies would create an import cycle. `ProposalExecution` is the sole standing-contract naming gap: the original `DAO_Execute` executes inline, while Concordia requires a distinct authorized Executable contract.

**Deliberately local arithmetic:** `Cap.Governance.Utils.Count.rule`, `shareOfTotal` and `shareOfVotes` are not called. `rule` composes a quorum and single tally verdict, but does not supply this package's early/outstanding-vote logic. `shareOfTotal` counts only `Some` votes as turnout, whereas quorum here includes abstentions. `shareOfVotes` selects exactly one qualifying option over voted weight; it cannot represent `OfAll`'s whole-electorate basis or the multi-pick denominator (weight of voters who picked, counted once per voter). `Types.decide` uses the opening electorate and these distinct denominators instead.

`Signal`, `Choose`, `SetInfo`, `SetRules`, `SetPublic`, `SetSettings` and `Dissolve` can flow through Action authorization and Executable execution. `SetShares` has no executable: shares change administratively via `DAO_ChangeShares`. `DAO_Apply` is separately callable with **joint provider and creator authority**; interface execution is not a vote-only enforcement boundary for that choice. It is not renamed `DAO_Execute`: the original choice executes a passed proposal, while this choice accepts an effect directly. `DAO_Open` remains on DAO because the creator opens a separately created Action with an electorate snapshot; the original `Member_Propose` is controlled by the member and creates the proposal itself. `Account_CreateDAO` retains the original name for account-led founding, without implying a vote-gated founding path. `Ballot_Consume` remains distinct from original `Ballot_Count` (which records a counted ballot) and `Ballot_Withdraw` (voter-controlled): here the owner consumes ballots. `BallotV2` and `Comment` are absent rather than relabeled; no equivalent responsibilities exist in this package.
